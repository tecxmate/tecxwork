Atomic bookings under pressure.

The core booking path is built for event-day bursts. When two recruiters or admins act at the same time, Postgres locks the candidate row and claims exactly one available interviewer slot.

01 request
Student applies for a specific company and time.
The application starts pending, so the system captures demand before spending capacity.
02 lock
Recruiter accepts; DB takes an advisory lock.
Concurrent accepts for the same student/time are serialized to prevent conflicting confirmations.
03 claim
`SKIP LOCKED` claims one free interviewer.
Other concurrent transactions skip locked rows and choose another free slot instead of colliding.
